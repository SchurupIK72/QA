# Промпт: Анализ конфликтов между документами ТЗ

## Назначение

Этот промпт предназначен для автоматического анализа нескольких документов технического задания (ТЗ, ГДД, дополнительных спецификаций) с целью выявления:

- Прямых конфликтов между требованиями
- Неоднозначных или противоречивых формулировок
- Отсутствующих разделов и требований
- Дублирования и путаницы в терминологии
- Пробелов в покрытии сценариев

---

## Входные данные

Для анализа необходимо предоставить:

1. **Основной документ ТЗ/ГДД** — базовый источник требований
2. **Дополнительные документы (ДопТЗ)** — изменения, правки, дополнительные спецификации
3. **Существующий отчёт ревью** (опционально) — для сверки с уже найденными проблемами

> ⚠️ **ВАЖНО: Правило приоритета документов**
> 
> **Дополнительное ТЗ (ДопТЗ) всегда имеет приоритет над основным ГДД.**
> 
> Если требования в ДопТЗ отличаются от ГДД, считаем что:
> - Требование из ДопТЗ — **УТВЕРЖДЕНО** и актуально
> - Требование из ГДД — **устарело** и требует обновления
> - Расхождение — это не конфликт, а **утверждённое изменение**
>
> Конфликтом считается только противоречие **внутри** одного документа или отсутствие ясности в самом ДопТЗ.

---

## Структура анализа

### 1. УТВЕРЖДЁННЫЕ ИЗМЕНЕНИЯ (из ДопТЗ)

Поиск расхождений между ГДД и ДопТЗ. **Все изменения из ДопТЗ считаются утверждёнными.**

#### 1.1 Изменения механик

| Критерий | Что искать |
|----------|------------|
| Управление | Различия в описании джойстика, кнопок, жестов |
| Игровой цикл | Изменения в описании уровней, волн, сессий |
| Интерфейс | Добавление/удаление элементов UI |
| Формулы и расчёты | Новые формулы для показателей |

#### 1.2 Изменения значений

| Критерий | Что искать |
|----------|------------|
| Числовые значения | Время, дистанции, проценты, коэффициенты |
| Лимиты и ограничения | Максимумы/минимумы |
| Размеры и масштабы | Габариты объектов |

#### 1.3 Изменения логики

| Критерий | Что искать |
|----------|------------|
| Порядок действий | Последовательность шагов |
| Условия триггеров | Когда что происходит |
| Зависимости | Что от чего зависит |

#### Формат документирования изменений:

```markdown
| Параметр | Значение |
|----------|----------|
| ~~Старое (ГДД)~~ | ~~[Что было в ГДД]~~ |
| **Новое (ДопТЗ)** | **[Что теперь в ДопТЗ]** |
| Раздел ДопТЗ | [Номер раздела] |
| Статус | ✅ **УТВЕРЖДЕНО** |
```

---

### 2. НЕОДНОЗНАЧНЫЕ ТРЕБОВАНИЯ

Поиск требований, которые описаны двумя или более вариантами без указания финального решения:

```markdown
Шаблон для документирования:
| № | Проблема | Где находится | Варианты | Рекомендация |
|---|----------|---------------|----------|--------------|
| X.X | [Описание] | [Раздел/Страница] | Вариант 1: ... Вариант 2: ... | [Что уточнить] |
```

---

### 3. ОТСУТСТВУЮЩИЕ РАЗДЕЛЫ

Проверка наличия обязательных разделов:

#### Для игрового ТЗ:

- [ ] Туториал (полное описание, не ссылка)
- [ ] Обработка ошибок (сетевые, пользовательские)
- [ ] Офлайн-режим
- [ ] Edge cases (граничные случаи)
- [ ] Критерии приёмки (Acceptance Criteria)
- [ ] Лимиты и ограничения (валюты, инвентарь, строки)
- [ ] Локализация (поддерживаемые языки, переключение)
- [ ] Push-уведомления
- [ ] Аналитика событий

#### Для API/Backend ТЗ:

- [ ] Схема базы данных
- [ ] API endpoints (полный список)
- [ ] Обработка ошибок (коды, сообщения)
- [ ] Авторизация и токены
- [ ] Rate limiting
- [ ] Валидация данных

---

### 4. ОШИБКИ В ДОКУМЕНТАЦИИ

Типичные ошибки для проверки:

| Тип ошибки | Что искать |
|------------|------------|
| Дублирование номеров | Одинаковые номера разделов |
| Битые ссылки | Ссылки на несуществующие разделы |
| Путаница терминов | Разные названия для одного понятия |
| Опечатки в формулах | Несоответствие переменных |
| Устаревшие данные | Ссылки на документы "от XX.XX.XXXX" без самих документов |

---

### 5. ПРОБЕЛЫ В ПОКРЫТИИ СЦЕНАРИЕВ

#### Позитивные сценарии (должны быть описаны):

- [ ] Успешная авторизация (все способы)
- [ ] Успешная регистрация
- [ ] Основной игровой цикл
- [ ] Успешные покупки
- [ ] Получение наград

#### Негативные сценарии (часто пропущены):

- [ ] Неверный пароль X+ раз
- [ ] Истечение токена
- [ ] Недостаток валюты при покупке
- [ ] Потеря соединения во время действия
- [ ] Попытка действия заблокированным аккаунтом
- [ ] Двойной клик на кнопку
- [ ] Выход во время транзакции

#### Edge cases (граничные случаи):

- [ ] Смена часового пояса
- [ ] Смена языка во время сессии
- [ ] Переполнение числовых значений
- [ ] Удаление аккаунта с активной подпиской
- [ ] Восстановление после краша

## Ключевые слова для поиска конфликтов

При анализе документов обращать внимание на ключевые слова, которые могут указывать на изменения:

### Слова-маркеры изменений:

- "Новая логика"
- "Изменение управления"
- "Что меняется"
- "Убираем"
- "Добавляем"
- "Теперь"
- "Ранее было"
- "Вместо"
- "Больше не"
- "Правки"

### Слова-маркеры неопределённости:

- "Вариант 1" / "Вариант 2"
- "Уточнить у заказчика"
- "Надо прикрепить"
- "TODO"
- "TBD"
- "Примечание для разработчика"
- "Нужна возможность переключения"

### Слова-маркеры требований к конфигу:

- "Вывести в конфиг"
- "Настраивается в Админ-панели"
- "Параметр должен быть настраиваемый"
- "Вынести в конфиг"

## Алгоритм работы

1. **Загрузить все документы** в контекст
2. **Построить карту разделов** — сопоставить разделы разных документов по теме
3. **Сравнить описания** одних и тех же механик/элементов
4. **Выявить расхождения** — записать в таблицу конфликтов
5. **Проверить наличие** обязательных разделов
6. **Найти ошибки** форматирования и ссылок
7. **Сформировать отчёт** по шаблону
8. **Создать чеклист** для согласования с заказчиком

